Evergreen Insurance Quote API: Containerizing with Docker

Lab 1

In this lab, you will package the Evergreen Quote API into a Docker container: a portable, self-contained unit that bundles the app, its dependencies, and its runtime so it runs identically on any machine. You will write a Dockerfile, build an image from it, and run the API inside a container.

This is Week 7 of Phase 3. The app you are packaging is the standalone Express API from Week 2 (the in-memory version, on purpose, so the container has no database to depend on). Next week, Kubernetes runs many copies of exactly this image.

You are not expected to become a container engineer. You are here to see what a container actually is, why "it works on my machine" stops being an excuse, and what your engineers mean by "build the image" and "run the container."

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

Containers are how nearly all modern software ships. "Containerize it," "the image is too big," "it builds but won’t run": these are everyday delivery conversations. After building and running one container yourself, each becomes concrete, and the leap to orchestration (next week) makes sense.

1.3. What’s Already Set Up on Your Lab VM

  • VS Code, a terminal, and Docker (check with docker --version).

  • The starter project: the Evergreen Express API (src/, package.json), a .dockerignore, and a Dockerfile with `TODO`s.

1.4. Open the Project

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-docker in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder and that Docker is available:

    pwd
docker --version

    pwd should end in Labfiles/evergreen-quote-docker, and docker --version prints a version line, which is all you need.

1.5. The Container at a Glance

The lab is four `TODO`s and three commands:

  1. Complete the Dockerfile (TODO 1-TODO 4): base image, dependencies, source, start command.

  2. Build the image (docker build): turn the recipe into a template, one cached layer per instruction.

  3. Run the container (docker run): start the API from that template, with the port mapped.

  4. Prove it: curl the API served from inside the container, then rebuild and watch the cache work.

Think of the image as a meal-kit box sealed at the factory (same contents wherever it ships) and the container as one cooked meal made from it: cook as many as you like, each identical.

 Tip

Each TODO comment in the Dockerfile already shows the exact instruction it expects, so the file doubles as an answer key. The lab also states what every command should print, so check the terminal after each step.

1.6. Understand What a Container Is

Before writing anything, fix the mental model:

  • A container is an isolated process on the host, sharing the host’s Linux kernel, not a full virtual machine. It starts in milliseconds and is megabytes, not gigabytes.

  • An image is the read-only template a container is created from. You build an image once and run many containers from it.

  • A Dockerfile is the recipe that builds the image, one layer per instruction.

Why this matters: The container vs. VM distinction is the whole reason containers took over: same isolation, a fraction of the overhead. Leaders who grasp this understand why teams can run dozens of services on one machine.

1.7. Write the Dockerfile

Open Dockerfile in VS Code. It contains four numbered TODO comments.

Read TODO 1 carefully: it is the only step where you replace an existing line. The other three ask you to add lines.

  1. TODO 1: start from a small official Node image. The starter file has a placeholder line, FROM scratch, which means "start from a completely empty image" and gives you no Node runtime. Delete that line and type this in its place:

    FROM node:22-alpine

     Important

    Replace the FROM scratch line. Do not leave it in the file. Docker treats every FROM as the start of a new build stage, so a Dockerfile with two FROM lines either fails to build or quietly builds something other than what you intend.

  2. TODO 2: copy package.json first, then install production dependencies. Add these two lines directly below the TODO 2 comment:

    COPY package.json ./
RUN npm install --omit=dev

  3. TODO 3: copy the rest of the source. Add this line directly below the TODO 3 comment, above the existing EXPOSE 3000 line:

    COPY . .

  4. TODO 4: set the command that runs when the container starts. Add this line at the end of the file, below the TODO 4 comment:

    CMD ["node", "src/index.js"]

  5. Save the file with File → Save (or Ctrl+S).

Check your work. Ignoring the comments, which have no effect on the build, your finished Dockerfile contains these instructions in this order:

FROM node:22-alpine

WORKDIR /app

COPY package.json ./
RUN npm install --omit=dev

COPY . .

EXPOSE 3000

CMD ["node", "src/index.js"]

You can leave the TODO comments in place or delete them. Only the instruction lines matter.

Why this matters: The order is deliberate. Because each instruction is a cached layer, copying package.json and installing before copying the source means Docker reuses the dependency layer when only your code changes, turning minute-long rebuilds into seconds. "Optimize the layer caching" refers to exactly this ordering.

1.8. Build the Image

  1. Return to the VS Code integrated terminal (Terminal → New Terminal if you closed it). You should still be in the Labfiles/evergreen-quote-docker folder. In the terminal, run the build, tagging the image with a name:

    docker build -t evergreen-quote-api .

  2. Watch the output: Docker runs each instruction as a numbered step (FROM, WORKDIR, COPY, RUN, …​) and reports the layers. The npm install step takes the longest; everything else is near-instant. When it finishes, list your images:

    docker images | grep evergreen-quote-api

    One line: your image, tagged latest, a few hundred megabytes (most of it the Node runtime).

    Figure 1. The recipe, executed: one numbered step per Dockerfile instruction, then the finished image in the list

  3. Now see the layer cache earn its keep. Make a trivial source change (open src/index.js and add a blank line at the end, then save) and rebuild:

    docker build -t evergreen-quote-api .

     Note

    This second build finishes in a moment, and the RUN npm install --omit=dev step is marked CACHED. Only the layers after the changed file were rebuilt. That is the payoff of copying package.json before the source, and it is what engineers mean by "the cache is warm."

Why this matters: The . at the end is the build context: the files Docker can see. The .dockerignore keeps junk like node_modules and .git out of that context, making builds faster and images smaller. A bloated image usually means a missing .dockerignore.

1.9. Run the Container

  1. Start a container from the image, mapping the port:

    docker run --rm -p 3000:3000 evergreen-quote-api

    You should see Evergreen Quote API running on http://localhost:3000. The terminal stays attached to the container; leave it running.

  2. Open a second terminal beside it (Terminal → Split Terminal, or Ctrl+Shift+5) and call the API running inside the container:

    curl http://localhost:3000/api/quotes

    You get the familiar JSON array of four quotes, q1 through q4, served from inside the container.

    Figure 2. The proof: the same API, now answering from inside a container

  3. Stop the container with Ctrl+C in the first terminal. Because you used --rm, Docker cleans it up automatically.

Why this matters: -p 3000:3000 maps a port on your machine to a port inside the container; without it, the API would run but be unreachable. "The container is running but I can’t connect" is almost always a port-mapping problem. You just wired it correctly.

1.10. Prove the Portability (Discussion)

  1. The image you built contains Node, your dependencies, and your code: everything the app needs. It will run the same way on a teammate’s laptop, a CI server, or AWS, with no "install Node first" step.

  2. That image can be pushed to a registry (Docker Hub, AWS ECR, GitHub Container Registry) and pulled anywhere, which is exactly how next week’s orchestration (Kubernetes/EKS) gets your app onto a cluster.

Why this matters: This is the payoff of containers: build once, run anywhere. The "works on my machine" problem disappears because the machine travels with the app.

1.11. Review

In this lab you:

  • Learned what a container, an image, and a Dockerfile are, and how they differ from VMs.

  • Wrote a Dockerfile with sensible layer caching (dependencies before source) and watched a rebuild hit the cache.

  • Used .dockerignore to keep the build context lean.

  • Built an image and ran the Evergreen API inside a container, with port mapping.

  • Saw why containers make software portable: the foundation for orchestration.

You packaged the Evergreen API the way virtually all modern software ships, and you are ready for next week, where many copies of this container are scaled and self-healed on Kubernetes.
